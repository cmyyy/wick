## 你要做的事

1. **先判断这个 issue 值不值得动手**。分三种判定：
   - `可处理`：问题描述清楚，能在代码里定位到原因，有明确的修法
   - `需补充信息`：描述含糊、缺少复现步骤、缺少环境信息
   - `不处理`：功能请求与本项目定位不符、重复 issue、问题本身不成立

2. **如果是 `可处理`**：在仓库里找到相关代码，说明根因在哪、要改哪个文件、改成什么样。**这一步只输出方案，不要改文件。**

3. **如果是 `需补充信息`**：列出具体要作者补充哪几条，越具体越好。

4. **如果是 `不处理`**：一句话说明理由。

## 输出格式（严格遵守，程序要解析）

第一行必须是判定结果，格式为 `判定：<可处理|需补充信息|不处理>`

然后按下面的结构写：

```
判定：可处理

原因：<2-3 句话说清这是什么问题、根因在哪>

涉及文件：
- `path/to/file.py` — 要改什么

改动要点：
1. <具体怎么改>
2. <具体怎么改>

需要批准的动作：<如果有需要批准才能做的事，写在这里，比如「提 PR」；没有就写「无」>

遗留 / 下一步：<还没做完、或下一轮该继续做什么；没有就写「无」>
下次跟进：<ISO 时间> <到时候做什么；没有就写「无」>
```

## 硬性要求

- 不要编造文件路径。只写你**实际在仓库里看到过**的文件。
- 不要在本次运行中修改任何文件、提交任何 commit、推送任何分支。
- 如果找不到相关代码，判定改为 `需补充信息` 并说明你找了哪些地方。
- `下次跟进` 只在确实需要过一会儿回来做时写，时间用 ISO 8601（例如 `2026-11-23T09:00:00+08:00`；不带偏移按本机时区），不要写「明天下午」这类说法。
