## T1 读码问答（你发起，4 条）

### T1-1 工具注册表在哪、怎么新增一个工具
- 输入：`工具是怎么注册的？我要加一个新工具改哪里？`
- 期望：指出工具注册的模块与关键类/函数；说明声明式注册路径
- 判定：答案命中 `tools/` 下的真实文件名 + 至少 1 个真实符号名（grep 存在）；**引用符号必须全部存在**（幻觉率 0）；轮次 ≤3

### T1-2 上下文压缩什么时候触发
- 输入：`对话太长时它怎么压缩？触发条件是什么？`
- 期望：指出压缩阈值配置项 + 触发点代码位置
- 判定：命中真实配置键名 + 真实模块路径；不含不存在的配置项；轮次 ≤3

### T1-3 cron 调度器怎么触发一个 job
- 输入：`定时任务到点是哪个模块触发的？流程走哪几步？`
- 期望：给出调度主循环 → 组装 prompt → 起会话的链路
- 判定：命中 `cron/` 下真实文件名 ≥2 个；描述顺序与代码一致；轮次 ≤3

### T1-4 会话状态存在哪、结构是什么
- 输入：`会话历史存在哪里？表结构大概什么样子？`
- 期望：指出 state.db + 主要表名/字段
- 判定：表名真实存在（查 sqlite schema 校验）；不虚构字段；轮次 ≤3

**T1 汇总指标**：定位准确率、幻觉符号率（红线 <2%）、平均轮次（≤3）

## T2 Bug 定位（你发起或 CI 失败触发，4 条）

> 做法：在目标仓库的临时 worktree 里**人为注入 4 个 bug**（不提交主干），让它定位。

### T2-1 空引用
- 注入：某函数在配置项缺失时直接取值未判空
- 输入：`切到这个配置项没配的环境，服务启动就崩，报 AttributeError，在哪？`
- 判定：指到注入文件与函数；根因说对（未判空）；轮次 ≤4

### T2-2 边界条件
- 注入：分页逻辑在 `page_size=0` 或最后一页时少取一条
- 输入：`分页接口最后一页总少一条数据`
- 判定：指到真实函数；指出 off-by-one 位置；轮次 ≤4

### T2-3 并发/竞态
- 注入：共享状态在并发下被覆盖（去掉锁或改成非原子操作）
- 输入：`压测时偶尔出现计数偏少，单线程跑不出来`
- 判定：指到共享状态位置；说出竞态原因；轮次 ≤5

### T2-4 资源泄漏
- 注入：异常路径没有释放资源（文件/连接/子进程）
- 输入：`跑一段时间句柄数一直涨，最后报 too many open files`
- 判定：指到未释放的资源点；说明异常路径；轮次 ≤5

**T2 汇总指标**：定位准确率（指对文件+函数才计）、平均轮次

## T3 出补丁（含 commit/PR 描述，4 条）

> 在 worktree 里跑；判完丢弃。

### T3-1 加参数
- 任务：给某函数增加一个可选参数，保持向后兼容
- 判定：全部测试通过 + **无回归**（原有测试全绿）+ diff 只碰相关文件 + commit message 与实际改动一致

### T3-2 修边界
- 任务：修复 T2-2 的 off-by-one
- 判定：新增/修改的测试能覆盖该边界 + 无回归 + diff ≤ N 行（改动最小性）

### T3-3 重命名/重构
- 任务：把一个内部函数改名并更新所有调用点
- 判定：无遗留旧名（grep 校验）+ 测试通过 + 未改动无关文件

### T3-4 修一个真实 issue
- 任务：从目标仓库挑一个已关闭的简单 issue，按描述修
- 判定：能复现问题 → 修后测试通过 + 无回归 + PR 描述逐条对应实际 diff（**描述里出现的每个改动点都能在 diff 里找到**）

**T3 判定（四层 grader，v1.2）**：
1. **硬门槛**：全部测试通过 + 无回归（原有测试全绿）
2. **质量 rubric**（1-5 分，不设及格线）：任务理解 / 是否找对地方 / 正确性 / 有没有补测试 / **改动最小性**
3. **轨迹指标**（脚本算）：`edits per test failure`、`reverts/retries 比`、无关文件触碰数
4. **描述一致性**：PR/commit 描述里提到的每个改动点，都能在 diff 里找到

**T3 汇总指标**：改对率、回归失败率（红线 **0**）、rubric 均分、轨迹三项、描述一致性

## T4 写测试（4 条）

### T4-1 给纯函数补单测
- 任务：给某纯函数补单测（正常 + 边界 + 异常）
- 判定：测试能跑通 + 三类用例齐全

### T4-2 变异验证（关键）
- 任务：给某函数补测试；判完在源码里**注入一个 bug**（改一个判断符号），再跑测试
- 判定：**注入 bug 后测试必须失败**（否则测试无效，只测了 happy path）

### T4-3 覆盖异常分支
- 任务：给一个有很多 try/except 的函数补测试
- 判定：至少覆盖 1 条异常路径（用覆盖率或"注入异常必失败"验证）

### T4-4 不写假测试
- 判定：测试中不得 mock 掉被测对象本身；不得 assert 恒定值；不得只断言不抛异常

**T4 汇总指标**：测试有效性（变异检出率）、异常分支覆盖

## T5 主动巡检（它自己发起，4 条）

### T5-1 CI 失败自动响应
- 场景：注入一次测试失败提交
- 判定：**8 分钟内发现** + 定位到失败用例 + 给出修复建议或补丁；误报 0

### T5-2 新 issue 判断值不值得修
- 场景：投喂 2 条 issue（1 条真 bug、1 条无效吐槽）
- 判定：真 bug 识别率 100%；**无效的不打扰**（符合"少占注意力"原则）

### T5-3 PR review
- 场景：投喂 1 个带缺陷的 PR（如漏边界判断）
- 判定：指到**具体文件行** + 说清风险；不刷无意义评论（噪音 ≤1 条）

### T5-4 依赖漏洞
- 场景：引入一个有已知漏洞的旧版本依赖
- 判定：发现 + 指出包名/版本/建议版本

**T5 汇总指标**：必推漏报（红线 **0**）、误报 ≤1 次/天、意见定位到行率

## 评测对象（v1.2 关键，别混为一谈）

| 对象 | 怎么跑 | 回答什么问题 |
|---|---|---|
| **① 模型基线** | **最小 harness**（只给 bash + 编辑器，不给 Router/Worker），同一个模型 | 底数：裸模型在这些任务上什么水平 |
| **② 架构增益**（主指标） | 完整架构 vs ①，同一批用例同一模型 | **我的 Router / 事件驱动到底加了多少分** |
| **③ 在线使用** | 真实自用一周 | 接受 / 拒绝 / 大改 分布 |

> SWE-bench 用最小 harness 是为了公平比模型、排除 harness 影响；本项目相反——harness 就是贡献。所以基线用最小 harness，增益必须 A/B 对比，否则测出来只是"模型行"。
