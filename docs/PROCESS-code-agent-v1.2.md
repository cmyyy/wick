# Code Agent 开发框架 v1.2

> 项目：在 Hermes 上复现 DeepSeek Super-agent 的双层架构，做一个能主动接活的 code agent。
> 定位：**读透一个框架 → 读懂一套新架构 → 在两个之间做迁移实现**。不是 fork，不是跑别人的 demo。
> 本文是项目纲领，所有阶段、验收、评测都以此为准。
>
> **v1.2 修订**：修掉 6 处"不同出处强行拼装"的冲突——最重要的一条是分清「测模型水平」和「测我的架构增益」，否则评了半天只证明模型行。

---

## 0. 四条红线

1. **不改 Hermes 内核**，只在 plugins / skills / hooks / config 层扩展（保证能跟上上游升级）
2. **不声称从零开发**。对外讲"在开源 Agent 框架上扩展"；简历写能力与结果，不写框架名
3. **数字必须真实**。没跑出来的指标不写进简历；跑不通就诚实说跑不通
4. **不同来源的结论不跨规模搬运**：大厂/学术环境的结论（r 值、p95 收益、200 agent 组织经验）只当线索，不当预期

## 1. 六阶段流水线

| # | 阶段 | 产出物 | 过闸条件（不达标不进下一阶段） |
|---|------|--------|------------------------------|
| 0 | 能力定义 | T1-T5 任务分类 + 每类"成功长什么样" | 每类都能判定对错 |
| 1 | 评测地基 | 私有评测集 + 隐藏/变形测试 + rubric + judge 校准 + 跑分脚本 | 一条命令出 JSON 报告 |
| 2 | 架构设计 | 扩展点决策表 + 工具契约 + 权限模型 + 路由策略 | **先跑 baseline**；每个复杂度增量都要比 baseline 好，否则删掉 |
| 3 | 分层实现 | L1 Router 路由 → L2 Worker 执行 → L3 事件驱动 → L4 失败恢复 | 每层比上一层好，否则回退 |
| 4 | 评测验证 | ①模型基线 ②架构增益 A/B ③在线自用 | 达到红线指标 |
| 5 | 部署上线 | CLI + 沙箱 + 三级权限 + 监控 | 陌生 repo 能跑通且不改坏 |

## 1.5 任务分类（阶段 0 产物）

| # | 任务 | 谁发起 | 成功标准 |
|---|------|--------|---------|
| **T1** | 读码问答 | 用户问 | 定位真实文件与函数、零幻觉、轮次 ≤3 |
| **T2** | Bug 定位 | 用户问 / CI 失败 | 指对位置 + 因果链清楚 |
| **T3** | 出补丁（**含 commit / PR 描述**） | 用户问 | 测试过 + 无回归 + 质量 rubric 达标 + 轨迹干净 |
| **T4** | 写测试 | 用户问 | 能跑通 + **能抓到注入的 bug**（变异验证） |
| **T5** | 主动巡检（CI / issue / review PR / 依赖漏洞） | **它自己** | 发现不漏（8 分钟内）、误报 ≤1 次/天、意见指到具体代码行 |

## 2. 架构：Super-agent 五模块 → Hermes 落点

| Super-agent 模块 | 职责 | Hermes 现有能力 | **你要写的** |
|---|---|---|---|
| **双层：Router** | 接指令、判性质、分派、维护全局上下文 | 主 agent loop、delegation | **路由决策逻辑** |
| **双层：Worker** | 隔离会话并发执行，不直接回用户，向 Router 汇报 | 子 agent（delegation） | **Worker 结果契约**：状态/产物/失败原因结构化回报 |
| **事件驱动** | 持续监控 IM / GitHub / CI | cron + 外部触发 | **双筛网**：规则过滤 + 语义判断 |
| **异步多信道** | 不同信道定制交互规范 | 飞书 / 桌面 / CLI | **信道输出策略** |
| **存算分离** | 计算、状态、环境分离 | state.db | **任务级 trace**（可回放） |
| **Watchdog** | 异常恢复 | 进程守护 | **卡死检测 + 自动重启 Worker** |

> ⚠️ Super-agent 官方明确说：实验基于**合成负载与简化环境，不是产品结论**。它的 p95 收益数字（29.5→15.7 min）**只作方向参考，本项目不复现、不承诺**。

### 注意力经济（核心设计原则）

> 尽可能少占用人的注意力，尽可能多地提供价值。

| 级别 | 什么情况 | 行为 |
|---|---|---|
| **必推** | CI 失败 / 任务失败 / 需要拍板 / 有产物可验收 | 立即通知 |
| **聚合** | 待办到期、小改动完成、例行报告 | 攒到固定时间说一次 |
| **沉默** | 过程性输出、无价值信息、自己已解决 | 不说 |

判定依据：**可逆性 × 影响**。

## 3. 评测体系

### 3.1 三个评测对象（v1.2 关键修订：别混为一谈）

| 对象 | 用什么 harness | 回答什么问题 |
|---|---|---|
| **① 模型基线** | **最小 harness**（只给 bash + 编辑器，不给 Router/Worker） | "裸模型在同样任务上什么水平"——这是底数 |
| **② 架构增益**（主指标） | **我的完整架构** vs **同一个模型 + 最简 harness** | "**我的 Router/事件驱动到底加了多少分**" |
| **③ 在线使用** | 真实使用一周 | 接受/拒绝/大改分布 |

> SWE-bench 官方刻意用最小 harness 是为了**公平比较模型**（排除 harness 影响）。本项目相反——**harness 就是贡献**。所以基线用最小 harness，增益必须 A/B 对比，否则测出来只是"模型行"。

### 3.2 判"改动好不好"：四层 grader

| 判据 | 怎么判 | 性质 | 出处（可靠度） |
|---|---|---|---|
| **① 测试通过 + 无回归** | 确定性判定 | **硬门槛** | SWE-bench Verified（一手）/ Anthropic evals（一手） |
| **② 质量 rubric 打分**（1-5，非阈值） | Issue 理解 / 找对地方 / 正确性 / 有无补测试 / **Patch Minimality** | 打分维度 | AdaRubric（arXiv 2603.21362，一手论文，**但 r=0.79 是 300 条轨迹的实验值，本项目规模不引用**） |
| **③ 轨迹指标**（脚本算，零成本） | **分两层**（见下） | **硬指标** | futureagi 2026（二手博客）/ AgentLens（一手论文） |
| **④ judge 校准** | 人工标 10-20 条，报「**与人工一致 N/M 条**」 | 一次性 | agentpatterns.ai（二手博客，仅采纳"必须校准"这个结论） |

#### 轨迹指标要分两层算（v1.2 修订）

| 层 | 指标 | 高了说明 |
|---|---|---|
| **Router** | 路由准确率（该自己做的没派出去 / 该派的没派）、重复派活率、上下文同步丢失次数 | 分派逻辑有问题 |
| **Worker** | edits per test failure、reverts/retries 比、无关文件触碰数 | 找错地方 / 不会回滚 / 边界失控 |

> 原做法直接套 single-agent 的 edits/failure，双层架构下会混淆责任——Worker 的乱试和 Router 的错派是两回事。

**为什么必须看轨迹**：两个 agent 都让测试通过——A 失败后回滚换方案，B 在失败上一路叠到把测试改绿。只看结果分不出，而 B 埋雷。

### 3.3 三条硬规则

1. **防过拟合**：测试通过 ≠ 改对了。每条任务配隐藏测试或变形测试（UTBoost, ACL 2025，一手）
2. **报成绩必须注明 harness**：说清是"最小 harness 基线"还是"完整架构 A/B"，并给条数
3. **读 transcript**：每轮抽 5 条人工看过程（Anthropic evals 明确要求）

### 3.4 红线指标

| 指标 | 阈值 |
|---|---|
| 回归失败率 | **0** |
| 幻觉文件名/符号率 | < 2% |
| 平均轮次 | ≤ 5 |
| 必推事件漏报 | **0**（发现时限 8 分钟） |
| 单任务成本 | < 自定阈值 |
| **架构增益** | 完整架构必须比最小 harness 基线**更好**，否则这套架构没意义 |

## 4. 部署与安全

| 项 | 做法 |
|---|---|
| 隔离 | 每任务一个 git worktree；执行在子进程/容器，限 CPU / 内存 / 时间 |
| 权限 | **三级**：deny → allow → human gate，按可逆性 × 影响分类 |
| **最终判分隔离** | **在干净容器里跑评分，撤销 agent 对测试文件的一切修改**（防它改测试骗分） |
| 输出契约 | **只看仓库改成了什么**，不解析 agent 的最终文本 |
| 预算 | 步数 / 时间 / token 上限，超限中止并汇报 |
| 监控 | 任务类型、步数、token、是否通过测试、失败原因分类 |
| ~~分级合并门禁~~ | **暂不启用**：那是"管 200 个 agent、每 30 分钟巡检 PR"的组织经验，个人项目没有 PR 流量。等真有外部 PR 流再开 |

## 5. 迭代制度

| 制度 | 做法 |
|---|---|
| **LESSONS.md 错题本** | 每次任务结束记一条：哪个改动不该合、哪个测试没跑够 |
| **复盘 → 改 playbook → 生效** | 个体错误写进 skill/prompt，下次自动带上 |
| **周期例行代替持续记忆** | 靠固定例程（晨间汇总、周审计），不指望上下文记住整个工作流 |
| **经验沉淀成 skill** | 一次成功的做法立刻写成 skill |

**委托判断标准**：**重复 > 难度**——每天一次以上、有固定模式的事才值得自动化。
